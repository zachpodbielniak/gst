** libregnum (LRG) backend caveats
:PROPERTIES:
:CUSTOM_ID: lrg-backend-caveats
:END:
These are expected limitations of the optional =--lrg= backend (see
[[file:lrg-backend.org][LRG Backend]]), not bugs:

- =PRIMARY= selection maps to the system clipboard (raylib/GLFW exposes only
  one clipboard), so middle-click paste returns the last copied/selected text.
- =--lrg=3d= and =--lrg=3dvr= are reserved and rejected at startup; only =2d=
  is implemented.
- The window repaints at ~60fps while open (immediate-mode rendering).
- Window transparency is applied at the window level, not per-cell.
- =--lrg= opens a separate raylib/OpenGL window and does not support embedding
  via =--windid=.

*** Plain left-click behaved like a drag (RESOLVED)
:PROPERTIES:
:CUSTOM_ID: click-behaves-like-drag-resolved
:END:
*Status:* Fixed in 0.4.1
*Affects:* Mouse input / text selection (=GstSelection=, =main.c=), all backends (X11, Wayland, LRG)

A plain left-click-and-release was treated as a click-and-drag. This showed up two ways depending on whether the running program had mouse reporting enabled:

1. *Local selection* -- at a normal shell prompt, a click left the clicked cell highlighted instead of selecting nothing.
2. *Mouse-reporting apps* -- inside tmux (with =mouse on=), vim, etc., a click on a pane started a copy-mode/drag selection instead of just clicking (e.g. switching the active tmux pane). Other terminals like kitty handle this correctly.

Both came from the same cause: the ~1px of pointer jitter present in almost any real click produces a single mouse-motion event in the *same* cell as the press, and that motion was being treated as the start of a drag.

- For local selection, =gst_selection_extend()= promoted the selection =EMPTY -> READY= on the first motion even when the pointer never left the starting cell, defeating the "click with no drag clears on release" safeguard and leaving a one-cell highlight.
- For mouse reporting, =on_button_press()= reset the motion-dedup baseline (=last_mouse_col/row=) to =-1=, so the first same-cell motion after a press always passed the dedup check and was reported to the application as a drag.

/Fix:/ Two complementary changes, both keyed on "did the pointer actually leave the press cell":
- =gst_selection_extend()= now stays =EMPTY= until the pointer moves to a *different* cell than where the button was pressed (covered by =tests/test-selection.c=).
- =on_button_press()=/=on_button_release()= now seed the motion-dedup baseline with the press/release cell instead of =-1=, so same-cell jitter is not reported as motion. A real cross-cell drag still reports and selects normally.

*** Large paste truncated, leaving tmux stuck in bracketed-paste mode (RESOLVED)
:PROPERTIES:
:CUSTOM_ID: large-paste-truncated-resolved
:END:
*Status:* Fixed in 0.3.8
*Affects:* Core PTY I/O (=GstPty=), all backends

Pasting a large block (300+ lines) into a program running under the terminal -- for example from one tmux pane to another -- truncated the paste to roughly the first ~4 KB (~190 lines). Afterwards the receiving application was left broken: the tmux prefix key (=C-b=) stopped responding, and further keystrokes appeared as stray escape sequences in other panes.

The PTY master fd is non-blocking (=G_IO_FLAG_NONBLOCK= is applied to the underlying fd, not just the =GIOChannel= wrapper). =gst_pty_write()= looped on partial writes but treated =EAGAIN= as a fatal error and =break='d out of the loop, silently discarding every unwritten byte. Once a paste overflowed the slave tty's ~4 KB input buffer, the next =write()= returned =EAGAIN= and the remainder -- including the closing bracketed-paste =ESC[201~= marker appended in =on_selection_notify()= -- was dropped. With the terminator missing, the receiving application stayed in bracketed-paste mode and consumed all subsequent input as paste body.

/Fix:/ =gst_pty_write()= now queues any bytes the kernel cannot accept immediately into an output buffer and drains them from a =G_IO_OUT= watch as the fd becomes writable, rather than dropping them. The entire paste (including the =ESC[201~= terminator) is always delivered, the main loop is never blocked, and the existing read watch keeps draining the child's output so the two directions cannot deadlock. =gst_pty_write_no_echo()= stays synchronous for small control replies so its =tcdrain()= / echo-restore semantics are unchanged. Covered by =tests/test-pty.c=.

*** Yazi image preview broken with kittygfx module (RESOLVED)
:PROPERTIES:
:CUSTOM_ID: yazi-image-preview-broken-with-kittygfx-module-resolved
:END:
*Status:* Fixed
*Affects:* kittygfx module (kitty graphics protocol)

When using yazi (terminal file manager) with the kittygfx module enabled, multiple symptoms appeared:

1. *'d' key auto-triggered on startup* -- yazi's delete confirmation dialog appeared without user input
2. *Error text visible in yazi UI* -- =Gi=537;EINVAL:failed to decode image= rendered as text
3. *Jump to last entry* -- yazi jumped to the bottom of the file list (as if Shift+G was pressed)
4. *Images rendered but old images persisted* -- switching to a smaller image left the previous larger image's pixels on screen

*** Root Causes and Fixes
:PROPERTIES:
:CUSTOM_ID: root-causes-and-fixes
:END:
The issue had multiple interacting root causes, each requiring a separate fix:

*1. PTY Echo Cascade*

When the module wrote a response (e.g. =\033_Gi=31;OK\033\\=) to the PTY, the line discipline echoed it back if =ECHO= was enabled. The echoed APC was re-parsed as a transmit command, failed to decode the status text as base64, generated an error response, which echoed again -- creating an infinite loop. Characters from error messages (=d= from "decode", =G= from response prefix) leaked to yazi as keypresses.

/Fix:/ Three-layer echo detection: response queue matching, structural heuristic (error codes contain =:= which is not in the base64 alphabet), and =gst_pty_write_no_echo()= for kernel-level echo suppression.

*2. Broken Zlib Decompression*

The original decompression used =g_converter_convert()= with a fixed-size output buffer and a retry loop that re-fed already-consumed input, corrupting the decompressor state. This caused every zlib-compressed image to fail decoding.

/Fix:/ Rewrote decompression to use =GConverterInputStream= wrapping a =GZlibDecompressor= -- the streaming approach handles arbitrary compression ratios without fixed buffers or state corruption.

*3. Chunked Transfer ID Assignment*

Continuation chunks (with =image_id == 0=) were auto-assigned new IDs instead of reusing the first chunk's ID. Each chunk became a separate incomplete upload that never finalized.

/Fix:/ Added =last_image_id= tracking to the cache. Continuation chunks reuse the active upload's ID when =image_id == 0=.

*4. First-Chunk Fields Lost on Continuation*

The =quiet=, =action=, =placement_id=, pixel format, and all display parameters were only present in the first chunk. Continuation chunks carried parser defaults (e.g. =quiet=0= instead of =quiet=2=, =action='t'= instead of =action='T'=). Using these defaults for the final response and placement creation produced wrong behavior: OK responses sent when they should be suppressed, placements not created because action appeared to be transmit-only.

/Fix:/ All first-chunk control keys are stored in the =GstKittyUpload= accumulator struct and used when the final chunk triggers decode and placement.

*5. Quiet Flag Logic Inverted*

Success responses used =cmd->quiet != 1= which incorrectly sent OK for =q=2= (suppress all). Per the spec: =q=0= sends all, =q=1= suppresses OK, =q=2= suppresses everything.

/Fix:/ Changed to =saved.quiet == 0= for success responses.

*6. Stale Image Pixels After Delete*

Yazi's image transition pattern sends =a=d,d=A= (delete all) before uploading a new image. The delete correctly removed placements from the cache, but the terminal's dirty-line tracking didn't know about it -- the text under the old image hadn't changed, so those lines weren't redrawn. Old image pixels persisted in the pixmap.

/Fix:/ After processing delete commands, the module explicitly calls =gst_terminal_mark_dirty(term, -1)= to force a full repaint.
